# Auditoría de Seguridad y Producción — Car Wash SaaS

**Fecha:** 2026-05-18
**Rama:** `new`
**Alcance:** Middleware, NextAuth, guards client-side, API handlers, webhooks, crons, configuración env y multi-tenancy.

> Severidad: **🔴 crítica** · **🟠 alta** · **🟡 media** · **🔵 baja**

---

## Resumen ejecutivo

Se identificaron **5 hallazgos críticos** que permiten escalación de privilegios, cross-tenant data access (IDOR) y exposición de credenciales. La causa raíz común es que la capa de autorización se delegó a un cookie/cabecera que el cliente puede modificar (`selected-tenant` / `x-tenant-slug`) sin re-verificar membresía del usuario al tenant en el handler.

Adicionalmente se encontraron problemas de redirección post-login, fugas momentáneas de UI a empleados, configuración de cookies y dominio frágil entre producción y desarrollo, y código duplicado/generado obsoleto en el repo.

## 🔴 Hallazgos críticos

### C-01 · IDOR cross-tenant: cualquier usuario autenticado puede leer/escribir datos de otro lavadero

**Archivos:** todos los handlers en
- [src/modules/clients/handlers/](src/modules/clients/handlers/)
- [src/modules/vehicles/handlers/](src/modules/vehicles/handlers/)
- [src/modules/orders/handlers/](src/modules/orders/handlers/) (excepto los `/api/commissions/*` y `tenant/*`)
- [src/modules/services/handlers/get-services.handler.ts](src/modules/services/handlers/get-services.handler.ts), [src/modules/services/handlers/get-service-by-id.handler.ts](src/modules/services/handlers/get-service-by-id.handler.ts)

**Patrón vulnerable** (presente en ~20 endpoints):

```ts
const session = await requireAuth();
const { tenantId } = await requireTenantContext(request.headers); // ← lee header inyectado por middleware
// ❌ NUNCA se valida que session.user.id sea miembro de tenantId
const data = await service({ tenantId, ... });
```

`requireTenantContext` se limita a resolver el slug del header `x-tenant-slug`. El middleware ([middleware.ts:132-133](middleware.ts#L132-L133)) inyecta ese header a partir del cookie `selected-tenant`, **cookie que se setea/lee con `document.cookie` desde el cliente** ([src/lib/multitenancy/cookie.ts:19](src/lib/multitenancy/cookie.ts#L19)):

```ts
const cookieTenant = request.cookies.get("selected-tenant")?.value;
tenantSlug = cookieTenant || (token?.tenantSlug as string) || null;
```

**Exploit (paso a paso):**
1. Atacante crea cuenta y se loguea como OWNER del lavadero `victima-attacker`.
2. En DevTools: `document.cookie = "selected-tenant=lavadero-victima; path=/"`.
3. Visita `/api/orders`, `/api/clients`, `/api/vehicles/{id}`, etc. → recibe data del lavadero víctima.
4. Puede crear/editar/eliminar registros (POST/PUT/DELETE) en el lavadero víctima.

**Comparar con los handlers correctos** (en `src/modules/tenant/handlers/` y `commissions/`) que sí llaman `requireTenantAccess(session.user.id, tenantId, session.user.globalRole)`.

**Fix:** agregar en TODOS los handlers de recursos tenantizados, justo después de `requireTenantContext`:

```ts
await requireTenantAccess(session.user.id, tenantId, session.user.globalRole);
```

Idealmente unificar en un helper `requireTenantHandler(request)` que devuelva `{ session, tenantId, tenant, tenantUser }`.

### C-02 · Secrets en `.env` con credenciales reales

**Archivo:** [.env](.env)

- `AUTH_SECRET="car-wash-secret-key-change-in-production"` ← string descriptivo, no entropía.
- `DATABASE_URL` con credenciales Supabase de producción en texto plano.

- El secreto débil seguramente se usa también en producción (Vercel env). Permite forjar JWTs.
- El archivo local puede llegar a logs, backups, capturas o un commit accidental futuro.

1. Rotar inmediatamente: `AUTH_SECRET` (genera con `openssl rand -base64 32`), password Supabase, password de Gmail/App Password.
2. Verificar que el `AUTH_SECRET` configurado en Vercel/host es la nueva clave segura, no la cadena de ejemplo.
3. Auditar historial git: `git log --all -p -- .env` por si llegó a commitearse.

### C-03 · NextAuth: `secret` no se pasa explícito y cookie no se prefija como `__Host-`

**Archivo:** [src/lib/auth/index.ts](src/lib/auth/index.ts)

- El objeto pasado a `NextAuth({...})` no define `secret`. Depende de que NextAuth lo lea de `AUTH_SECRET`. Funciona, pero conviene declararlo explícito (y validar al boot que existe; hoy una variable vacía hace que NextAuth caiga al modo "Configuration" silenciosamente — el `LoginForm` ya lo trata como error genérico).
- La cookie de sesión usa prefijo `__Secure-` ([src/lib/auth/index.ts:9-10](src/lib/auth/index.ts#L9-L10)). Cuando hay un único dominio (no subdomains), `__Host-` ofrece mejor garantía porque rechaza `domain` attribute y obliga `path=/`. Si no se necesita compartir entre subdomains, migrar a `__Host-next-auth.session-token`.
- Falta `cookies.callbackUrl`, `cookies.csrfToken`, `cookies.pkceCodeVerifier` configuradas con `secure: true` y nombres adecuados. NextAuth aplica defaults pero en cross-subdomain se han visto inconsistencias.

**Adicional:** [middleware.ts:75-76](middleware.ts#L75-L76) usa `salt: cookieName`. Aceptable, pero debe **coincidir 1:1** con el salt usado al firmar (que NextAuth deriva del cookieName); cualquier cambio en uno requiere el otro o las sesiones se rompen.

### C-04 · Cron endpoints abiertos en desarrollo y fail-open en producción si la env no está

**Archivos:** [src/modules/cron/handlers/reminders.handler.ts:7-9](src/modules/cron/handlers/reminders.handler.ts#L7-L9), [src/modules/cron/handlers/plan-changes.handler.ts:7-9](src/modules/cron/handlers/plan-changes.handler.ts#L7-L9)

```ts
const cronSecret = request.headers.get("x-cron-secret");
if (cronSecret !== process.env.CRON_SECRET && process.env.NODE_ENV === "production") {
  return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
}
```

Problemas:
1. **Fail-open en non-prod:** cualquiera puede dispararlos en staging/preview. Estos endpoints modifican planes, generan facturas y envían mails — un atacante puede agotar Resend y spamear clientes.
2. **Fail-open si `CRON_SECRET` no está seteado en producción:** entonces `process.env.CRON_SECRET === undefined`. Si el header viene vacío (`null`), `null !== undefined` → 401 OK. Pero si el header trae `"undefined"` literal, `"undefined" !== undefined` → 401 también. OK ahí. El problema real: si el deploy se hace sin la variable, **el cron de Vercel real fallará silenciosamente** porque no enviará el secret esperado, y los recordatorios/cambios de plan dejarán de ejecutarse. No hay alerta.
3. **No usa comparación timing-safe** (`crypto.timingSafeEqual`).
4. `.env.example` ya menciona `CRON_SECRET` pero el `.env` local no lo tiene.

**Fix:**
```ts
const expected = process.env.CRON_SECRET;
if (!expected) {
  console.error("CRON_SECRET not configured");
  return NextResponse.json({ error: "Server misconfigured" }, { status: 500 });
}
const provided = request.headers.get("x-cron-secret") ?? "";
const ok = provided.length === expected.length &&
  crypto.timingSafeEqual(Buffer.from(provided), Buffer.from(expected));
if (!ok) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
```

### C-05 · Stripe webhook lanza si falta `STRIPE_WEBHOOK_SECRET`; ambos webhooks devuelven 500 genérico ante firma inválida

**Archivos:** [src/modules/webhooks/services/stripe-webhook.service.ts:13-17](src/modules/webhooks/services/stripe-webhook.service.ts#L13-L17), [src/modules/webhooks/handlers/stripe.handler.ts:16-19](src/modules/webhooks/handlers/stripe.handler.ts#L16-L19)

- `stripe.webhooks.constructEvent(..., process.env.STRIPE_WEBHOOK_SECRET!)` — el `!` no validó nada; si la env está vacía, Stripe lanza con mensaje confuso que el handler captura como 500 → Stripe interpreta como "reintenta". Genera ruido y nunca se aplica el evento.
- Al detectar firma inválida, el handler devuelve **500** en lugar de **400**. Stripe reintenta agresivamente con backoff exponencial → muchos errores duplicados en logs y posible saturación.
- Las acciones del switch (`updateTenant`, `connect plan`) **no son idempotentes**: si el mismo evento llega dos veces, el segundo intenta `plan: { connect: ... }` sobre algo que ya está conectado. Stripe envía duplicados; conviene guardar `event.id` procesado y deduplicar.
- [src/modules/webhooks/handlers/payu.handler.ts:35-37](src/modules/webhooks/handlers/payu.handler.ts#L35-L37) — el `GET` responde `{ status: "ok" }` con código 200 a cualquiera. Aceptable para health, pero podría usarse para reconocer la URL del webhook; mejor `204` sin body.

**Fix:**
- Validar `STRIPE_WEBHOOK_SECRET` al iniciar el módulo.
- Devolver 400 ante `Stripe.errors.StripeSignatureVerificationError`.
- Persistir `event.id` en una tabla `WebhookEvent` (o columna en `Payment`) y abortar si ya está marcada como procesada.

## 🟠 Hallazgos altos

### H-01 · Redirección post-login frágil y abierta a open-redirect (limitada)

**Archivo:** [src/components/forms/LoginForm.tsx:61-65](src/components/forms/LoginForm.tsx#L61-L65)

```ts
const rawCallback = searchParams.get("callbackUrl");
const destination = rawCallback && rawCallback.startsWith("/") ? rawCallback : "/dashboard";
window.location.href = destination;
```

- La verificación `startsWith("/")` previene URLs absolutas externas, pero **no detecta `//evil.com`** (URL relativa al protocolo): pasa el check y `window.location.href = "//evil.com"` redirige fuera del sitio.
- Tampoco bloquea `/\\evil.com` ni `/%2F%2Fevil.com` después de decode.
- No hay path-allowlist: cualquier endpoint cliente válido pasa, incluido `/api/...`.

Además, **el LoginForm no respeta el rol del usuario para destino**: un SUPER_ADMIN cae en `/dashboard` (que requiere tenant) y el middleware luego lo manda al modal selector. Es UX no-bug, pero confunde.

**Fix:**
```ts
function safeCallback(raw: string | null): string {
  if (!raw) return "/dashboard";
  // Permitir solo path absoluto local (un solo "/" inicial, no "//")
  if (!/^\/[^/\\]/.test(raw)) return "/dashboard";
  if (raw.startsWith("/api/")) return "/dashboard";
  return raw;
}
```

Y derivar el destino según rol/tenant:
```ts
if (session.user.globalRole === "SUPER_ADMIN") destination = "/admin";
```

### H-05 · Onboarding email + slug enumerables sin rate-limit ni captcha

**Archivos:** [src/app/api/auth/check-slug/route.ts](src/app/api/auth/check-slug/route.ts), `isEmailTaken` en [src/modules/auth/services/auth.service.ts:16-19](src/modules/auth/services/auth.service.ts#L16-L19)

- `GET /api/auth/check-slug?slug=foo` no tiene rate-limit. Un atacante puede enumerar todos los slugs (y por ende todos los lavaderos) en segundos. Combinado con login por empleado (que requiere slug), facilita el primer paso de un ataque dirigido.
- `isEmailTaken` se llama desde `/api/auth/register` antes de crear; con rate-limit de 10/h por IP. Pero responde un mensaje distinto a "email taken" vs "todo ok" → enumeración de emails con 10 intentos/hora por IP (rotación de IPs trivial).

**Fix:**
- Aplicar `checkRateLimit(`slug-check:${ip}`, { limit: 30, windowMs: 5*60*1000 })`.
- Para registro, responder genérico "Si la cuenta puede crearse te enviamos un correo de verificación" y manejar duplicados de forma asincrónica.

## 🟡 Hallazgos medios

### M-01 · Rate-limit in-memory en serverless no funciona

**Archivo:** [src/lib/security/rate-limit.ts](src/lib/security/rate-limit.ts)

El propio archivo lo documenta. En Vercel cada función puede tener múltiples instancias frías; el `Map` no se comparte. Un atacante con suerte (o suficiente paciencia) tira intentos hasta caer en otra instancia. El `setInterval` además **no se ejecuta entre invocaciones** en serverless (Vercel/Lambda freezan el event loop). El `Map` crece sin cleanup hasta que la instancia se recicla.

**Fix:** migrar a Upstash Redis (`@upstash/ratelimit`) o Vercel KV. El `.env` ya tiene espacio para credenciales.

### M-02 · `prisma.ts` ya no fuerza SSL para Supabase

**Archivo:** [src/database/prisma.ts](src/database/prisma.ts) (uncommitted)

El último commit (`132c554`) **agregó** SSL para no-localhost. Tu cambio en working tree **lo revierte**:

```diff
- const isLocalhost = connectionString.includes("localhost") || ...;
- const adapter = new PrismaPg({ connectionString, ...(!isLocalhost && { ssl: { rejectUnauthorized: false } }) });
+ const adapter = new PrismaPg({ connectionString });
```

Si tu `DATABASE_URL` ya incluye `sslmode=require` en el querystring, está OK. **El actual NO lo incluye** (`...?pgbouncer=true&connection_limit=1`). En producción Supabase **rechaza** conexiones sin SSL → reintentos infinitos en boot. Confirmar:
- Si conexión fluye en local pero no en Vercel: éste es el motivo.
- Solución: añadir `sslmode=require` al `DATABASE_URL` **o** restaurar el bloque `ssl: { rejectUnauthorized: false }`.

### M-03 · `DATABASE_URL` y `DIRECT_URL` apuntan al pooler

**Archivo:** [.env:1-2](.env#L1-L2)

Ambas usan `pooler.supabase.com:5432?pgbouncer=true&connection_limit=1`. `DIRECT_URL` debe **bypass pooler** (puerto 5432 directo) para que `prisma migrate`/`prisma db push` puedan ejecutar DDL sin que pgbouncer (transaction-mode) lo rompa. Comportamiento actual: probablemente funcionan los `db push` por casualidad, pero pueden fallar con prepared statements al haber DDL grandes.

**Fix:** `DIRECT_URL` debe ir al endpoint *direct* de Supabase (puerto 5432 con `?sslmode=require` y sin `pgbouncer=true`).

**Archivo:** [src/modules/auth/handlers/session-relay.handler.ts:52-58](src/modules/auth/handlers/session-relay.handler.ts#L52-L58)
